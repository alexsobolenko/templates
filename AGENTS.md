# AGENTS

Этот репозиторий — минимальный PHP 8.5 + MySQL шаблон TODO-приложения без фреймворка. Документ нужен как рабочая инструкция для агента и как антидот против лишней самодеятельности: сначала опираемся на фактический код и этот файл, а не на фантазии о "типичном Laravel/Symfony проекте".

## Главное правило

Агент не должен приносить в проект собственное представление о том, как "правильно" устроена система. Сначала он обязан распознать внутреннюю логику самого проекта: его точки входа, способ конфигурации, жизненный цикл, сложившиеся соглашения, границы между частями системы и уже существующие способы расширения. Только после этого допустимы изменения, и они должны рождаться из этой логики, а не подменять её внешними шаблонами, личными привычками агента или случайно удобным решением.

Иными словами: сначала нужно понять форму проекта, а уже потом писать код. Рабочего результата недостаточно, если он достигнут ценой нарушения внутренней целостности проекта.

Ни одна правка не должна быть сделана, пока агент не сверил её с `AGENTS.md`, стилем проекта и предыдущими замечаниями пользователя.

## Что здесь есть прямо сейчас

- Чистый PHP 8.5, автозагрузка PSR-4 через Composer (`App\\` -> `src/`).
- Статанализ и style-check через `PHPStan`, `PHP_CodeSniffer` и `Psalm`.
- Тесты выполняются через `PHPUnit` с отдельной test-БД и SQL-фикстурами.
- Очень маленькое MVC-подобное ядро:
  - `public/index.php` — точка входа.
  - `src/Core/App.php` — глобальный application state через статические свойства.
  - `src/Core/Http/Router.php` — роутер на PHP attributes.
  - `src/Core/DI/Container.php` — простой DI-контейнер на рефлексии.
  - `src/Core/Database/Database.php` — маленькая обёртка над PDO.
  - `src/Core/Controller/AbstractController.php` — `render()`, `json()`, `redirect()`.
  - `src/Core/Model/AbstractModel.php` — простейший Active Record через attributes `Table` и `Column`.
- SSR на обычных PHP-шаблонах в `views/`.
- Docker Compose окружение с `nginx`, `web` (php-fpm), `db` (MySQL), `mailcatcher` (Mailpit).
- Логгер в файл `var/log/app.log`.
- Небольшой демо UI и API:
  - `GET /`
  - `GET /{id}`
  - `POST /api/tasks`

## Что README обещает, но код пока не реализует полностью

`README.md` описывает целевую starter-template платформу: регистрация, авторизация, роли, email verification, reset password, CSRF, rate limiting, полноценный CRUD, admin panel, SQL schema/init и т.д.

На момент изучения репозитория этого в коде нет или есть только зачатки:

- нет готовой аутентификации и авторизации;
- нет middleware слоя;
- нет миграций, и агент не должен навязывать их проекту: для этого шаблона источником начальной схемы БД служат SQL-файлы в `.docker/mysql/init/`;
- нет `users` / `tasks` CRUD в полном виде;
- нет тестов, линтера и CI-конфигов;
- API `/api/tasks` сейчас только валидирует JSON и возвращает ответ, но не пишет в БД;
- форма в `views/site/index.php` отправляет обычный `application/x-www-form-urlencoded` POST на endpoint, который читает JSON из `php://input`, так что текущее поведение не следует считать "готовой фичей".

Если задача ссылается на README, агент обязан сверять ожидания с реальным кодом и явно разделять:

- "уже реализовано";
- "задекларировано как цель";
- "нужно дописать".

## Структура проекта

- `public/` — web root и входная точка.
- `src/Attribute/` — PHP attributes для роутов и ORM-метаданных.
- `src/Controller/` — HTTP-контроллеры.
- `src/Core/` — каркас приложения.
- `src/Enum/` — enum для низкоуровневых типов.
- `src/Exception/` — исключения по подсистемам.
- `src/Model/` — модели с `#[Table]` и `#[Column]`.
- `views/` — PHP-шаблоны и layout.
- `config/` — PHP-конфиги, сейчас фактически только `services.php`.
- `.docker/` — Dockerfile, nginx config, php.ini.
- `.docker/mysql/init/01_schema.sql` — текущая исходная SQL-схема для первоначальной инициализации БД в Docker.
- `var/log/` — runtime-логи.

## Источники правды по проекту

При любых изменениях приоритет такой:

1. Реальный код в `src/`, `views/`, `public/`, `config/`.
2. Этот `AGENTS.md`.
3. `README.md` как описание намерений и roadmap.

Если `README.md` противоречит коду, агент не должен молча "достраивать" отсутствующую архитектуру. Сначала нужно признать расхождение и работать от текущего состояния репозитория.

## Архитектурные договорённости

### HTTP и роутинг

- Роуты объявляются через `#[Route(...)]` на методах контроллера.
- Роутер сам сканирует `src/Controller`.
- Параметры пути вида `/{id}` мапятся по имени аргумента метода.
- DI для аргументов экшенов работает только для class-type параметров, которые контейнер может создать.
- Экшен обязан вернуть `App\Core\Http\Response`. Возврат массива, строки или `null` считается ошибкой.

### Контроллеры и views

- HTML-ответы рендерятся через `App\Core\Service\ViewRenderer`; `AbstractController::render()` должен быть тонкой обёрткой над ним.
- Используется layout `views/layout/main.php`.
- Во view обязательно экранировать пользовательские данные через `htmlspecialchars(..., ENT_QUOTES, 'UTF-8')`.
- Никаких Twig/Blade/Smarty сюда не тащить без явного запроса.

### DI и конфиги

- Контейнер по умолчанию создаёт классы рефлексией.
- Настройки конструктора можно передавать через `config/services.php`.
- Добавлять запись в `services.php` нужно только если авторазрешения недостаточно.

### Модели и БД

- Модели наследуются от `AbstractModel`.
- Таблица задаётся через `#[Table('...')]`.
- Поля задаются через `#[Column(...)]`.
- `save()` делает `INSERT` при `id === null`, иначе `UPDATE`.
- Для запросов используются только подготовленные выражения PDO.
- Проект опирается на SQL schema/init-файлы, а не на миграционный механизм.
- Если изменения касаются persistence-слоя, нужно проверить совместимость:
  - имена PHP-свойств в camelCase;
  - имена колонок в snake_case внутри `#[Column('...')]`;
  - nullable/primary/type в атрибутах.

### Ошибки и логи

- Глобальный обработчик исключений пишет в `var/log/app.log`.
- Ошибки обрабатываются централизованно в `src/Core/Service/ExceptionHandler.php`.
- Для HTML-ответов используется отдельное представление ошибки `views/error/page.php`, которое рендерится через `App\Core\Service\ViewRenderer`.
- Если в запросе есть `Accept: application/json`, обработчик должен возвращать JSON-ошибку; не нужно завязывать это решение на путь URL.
- HTTP-статус берётся из кода исключения, если он в диапазоне `400..599`, иначе используется `500`.
- Для текста ошибки приоритет у `exception->getMessage()`, но для `5xx` в non-debug режиме нельзя светить внутренние детали.
- Debug-детали допустимы только при включённом `APP_DEBUG`; проверка debug-режима живёт в `App`.
- Если меняется поведение ошибок, не надо молча ломать текущий минимализм; сначала сохранить простую предсказуемую модель.

## Практические команды

Основной способ поднять проект:

```bash
docker compose up --build
```

Полезные команды:

```bash
composer install
make lint
make test
docker compose ps
docker compose logs -f web
docker compose logs -f nginx
docker compose exec web composer dump-autoload
docker compose exec web php -l src/Controller/SiteController.php
```

Что важно помнить:

- контейнер `web` при старте уже выполняет `composer dump-autoload`;
- проект ожидает `.env` и опционально `.env.local`;
- текущие ключи окружения: `APP_ENV`, `APP_DEBUG`, `NGINX_PORT`, `MYSQL_PORT`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `MAILPIT_WEB_PORT`, `MAILPIT_SMTP_PORT`, `MAILER_DSN`, `MAIL_FROM_ADDRESS`, `MAIL_FROM_NAME`, `USER_ID`, `GROUP_ID`, `COMPOSER_VERSION`.
- `.env.example` не является обязательной частью этого репозитория и не должен считаться "отсутствующей проблемой", пока вы явно не попросите его добавить.
- Для статанализа используются `Makefile`, `phpstan.neon`, `phpcs.xml` и `psalm.xml`; при изменении структуры проекта их нужно держать в актуальном состоянии.
- Для тестов используются `phpunit.xml`, каталог `tests/`, отдельная БД `todo_list_test` и SQL-фикстуры; изменять этот контур нужно осознанно и синхронно.

## Ограничения и грабли, о которых агент обязан помнить

- Репозиторий может быть в грязном состоянии. Перед правками смотреть `git status --short` и не откатывать чужие изменения.
- В текущем worktree уже есть незакоммиченные и untracked изменения; это не повод что-то "почистить".
- `.env` в репозитории существует, но секреты из него нельзя пересказывать в ответах и документации.
- `vendor/` присутствует локально, но не надо полагаться на это как на архитектурное решение.
- SQL-инициализация уже есть в `.docker/mysql/init/01_schema.sql`; при изменениях модели/схемы нужно держать код и этот файл синхронными.
- `bootstrap/` сейчас пустой и не является активной частью приложения.
- Есть как минимум одно расхождение/подозрительное место в коде: `Router.php` импортирует `App\Exception\MethodNotAllowedException`, а фактический класс лежит в `App\Exception\Http\MethodNotAllowedException`. При смежных правках это нельзя игнорировать.

## Правила изменений

- Не делать широких рефакторингов без прямого запроса.
- Не менять стек и стиль проекта "для красоты".
- Не добавлять тяжёлые зависимости, фреймворки, ORM, шаблонизаторы, JS-сборку и фронтенд-фреймворки без явной команды.
- Конфиги линтеров и статанализа (`phpcs.xml`, `phpstan.neon`, `Makefile`-команды для линтеров и аналогичные файлы) менять только по согласованию с пользователем.
- Для команд разработки и линтеров не создавать одноразовые контейнеры через `docker compose run --rm`, если пользователь явно этого не просил; использовать уже запущенный контейнер через `docker compose exec`.
- Сначала править минимально и локально, затем при необходимости расширять.
- Если задача затрагивает `README.md`, обновлять его только в части, которая стала фактически правдой.
- Если меняется архитектура или workflow разработки, синхронно обновлять этот `AGENTS.md`.

## Ожидаемый стиль кода

- `declare(strict_types=1);` во всех PHP-файлах.
- Неймспейсы и структура каталогов должны соответствовать PSR-4.
- Классы в основном `final`, если нет причины для наследования.
- Сигнатуры методов и свойства по возможности типизированы.
- В PHP-коде поддерживать локальный стиль `phpdoc`: если в файле/модуле методы документируются через блоки `@param` / `@return`, новые и изменённые методы нужно оформлять так же, даже если типы уже указаны в сигнатуре.
- Агент обязан следовать локальному стилю кода, который закреплён существующим кодом проекта и конфигами линтеров/статанализа (`phpcs.xml`, `phpstan.neon`, `psalm.xml`, `Makefile`-команды проверки).
- Простота важнее абстрактной "гибкости".
- Комментарии добавлять редко и только там, где логика действительно неочевидна.

## Что делать агенту перед любой серьёзной задачей

1. Прочитать `README.md`, этот `AGENTS.md` и релевантные файлы модуля.
2. Проверить, что уже реализовано в коде, а что только заявлено.
3. Посмотреть `git status --short`, чтобы не задеть чужие изменения.
4. После правок прогнать хотя бы минимальную проверку:
   - `php -l` для затронутых PHP-файлов;
   - если менялся runtime/infra, то хотя бы `docker compose config` или релевантный запуск.

## Что делать агенту не надо

- Не обещать "полностью готовую" auth/task platform, пока её нет.
- Не додумывать БД-схему, роли и security-механизмы как будто они уже приняты в коде.
- Не навязывать проекту миграции, если задача не требует отдельного migration-механизма.
- Не переписывать текущий мини-каркас в более "правильную" архитектуру без запроса.
- Не скрывать найденные противоречия между кодом и документацией.
